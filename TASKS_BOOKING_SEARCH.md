# Поиск броней, теги и администрирование

Ветка: `feature/booking-search`. Доработана существующая реализация, миграции V1/V2 не изменялись. V3 объединяет прежние VIEWER/EDITOR в MODERATOR и обновляет ограничение ролей.

## Параметры списка броней

`GET /api/items`: `q`, `archived` (по умолчанию `false`), `status`, `fareClass`, `flightId`,
`passengerId`, `tag`, `urgency`, `priceMin`, `priceMax`, `departureFrom`, `departureTo`, `extraBaggage`.

Каждое слово `q` должно встретиться хотя бы в одном поле: коде брони, ФИО, e-mail, документе,
номере рейса, аэропортах или месте. До 100 символов и пяти слов. `%`, `_` и обратный слеш
экранируются и ищутся буквально. Статусы объединяются через «или», повторные `tag` — через «и».
Остальные фильтры объединяются через «и». Границы цены и дат включительны, даты вылета — UTC.

`sort=price,desc`: доступны `createdAt`, `updatedAt`, `price`, `departure`, `passenger`, `flight`,
`code`, `seat`, `status`. По умолчанию `createdAt,desc`; при равенстве используется ID.
`page` начинается с нуля; `size` от 1 до 100. Некорректные значения параметров, слишком большие
смещения страниц и неверные диапазоны дают 400 вместо ошибки сервера.

## Теги и массовые операции

- `GET /api/items/tags` — теги текущих броней с количеством.
- `PUT /api/items/{id}/tags` — `{ "tags": ["vip"], "version": 0 }`.
- `POST /api/items/bulk` — `{ "ids": ["UUID"], "action": "ADD_TAG", "tag": "vip" }`.

Действия: `ADD_TAG`, `REMOVE_TAG`, `SET_STATUS` (с `status`), `ARCHIVE`, `RESTORE`.
До 100 ID за запрос, повторные ID учитываются один раз. Ответ содержит `requested`, `succeeded`
и `failures` с ID, кодом брони, если он известен, и причиной отказа. Каждая бронь изменяется
в отдельной транзакции: конфликт версии одной записи не откатывает успешно обработанные записи.
Для всех действий действуют те же бизнес-правила, что для одиночных операций.

Теги приводятся к нижнему регистру, лишние пробелы убираются; до 40 символов и десяти тегов
на бронь. Архивные брони доступны только для чтения, кроме восстановления.
Брони доступны MODERATOR/ADMIN для чтения и изменения.

## Пользователи

Роли: MODERATOR («Модератор») и ADMIN («Администратор»). Модератор ведёт брони,
создаёт и редактирует рейсы и пассажиров. Удаление рейсов и пассажиров, управление
пользователями, аудит и окончательное удаление броней доступны только администратору.
Кнопки удаления справочников у модератора скрыты; прямой DELETE получает 403.
Миграция V3 при следующем запуске backend переводит VIEWER/EDITOR в MODERATOR,
объединяет дубликаты и сохраняет ADMIN. Существующие учётные записи и пароли сохраняются.

Только ADMIN. Список `GET /api/admin/users` поддерживает `q`, `role`, `enabled`, `page`, `size`,
`sort` (`login`, `displayName`, `createdAt`, `lastLoginAt`). Роль фильтруется по явно назначенной роли.

- `POST /api/admin/users`: `login`, `displayName`, непустой `roles`.
- `PUT /api/admin/users/{id}`: `displayName`, `roles`, обязательные `enabled` и `version`.
- `GET /api/admin/users/{id}` — актуальная версия.
- `POST /api/admin/users/{id}/reset-password` — новый временный пароль.
- `POST /api/admin/users/{id}/unlock` — снятие блокировки входа.

Временный пароль возвращается только при создании/сбросе и требует смены при входе.
Отключение отзывает refresh-сессии; JWT-фильтр проверяет активность и роли пользователя в БД.
Нельзя отключить себя, снять с себя ADMIN или сбросить собственный пароль через админку.
Проверка последнего активного администратора защищена блокировкой при параллельных запросах.
При 409 форма позволяет перечитать пользователя перед повторным сохранением.
